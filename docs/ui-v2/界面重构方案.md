# Gateway4j 管理界面重构方案（v2）

> 2026-11-04 · 配套原型：`gateway4j-admin-ui/prototype-v2/`（10 张可交互 HTML，截图在 `prototype-v2/shots/`）
> 约束：**旧前端完整保留**，新界面以并行形态落地，不删不改现有路由与行为。

---

## 一、现状诊断：为什么用户「看不懂」

| # | 问题 | 表现 | 根因 |
|---|------|------|------|
| 1 | **概念直译自后端实现** | 「分发路由/后置路由/前置/后置/作用域/阶段」直接暴露为表单字段与列名 | 界面按数据模型组织，而非按用户任务组织 |
| 2 | **表格为中心，零可视化** | 路由=一张表；插件=一行下拉；决策逻辑=一段 JSON | 没有任何一屏回答「流量从哪来、经过什么、到哪去」 |
| 3 | **画布藏得深** | RouteCanvas 是唯一可视化，但埋在路由列表动作里，入口不可见 | 可视化被当成「编辑器」而不是「说明书」 |
| 4 | **无反馈闭环** | 保存≠生效≠流量切换，用户不知道改完有没有用、影响谁 | 缺发布视图：无 diff、无灰度、无命中验证 |
| 5 | **出错难定位** | 5xx/超时只有数字，看不到「这一跳发生了什么」 | 缺请求级解释（调试台）与 hop 时间线 |

## 二、产品研究（同类可视化路由产品怎么做的）

| 产品 | 值得学的 | 原型吸收为 |
|------|----------|------------|
| **Traefik Dashboard** | 按 HTTP/TCP/UDP 分域；routers→services→middlewares 三对象始终可互跳；overview 一屏汇总 | 拓扑总览（P1）+ 路由详情链路（P7）的「对象互跳」 |
| **Kong Manager** | workspace 化导航；Service↔Route 树状关系；插件以卡片市场呈现 | 左侧分组 IA（P 全部）+ 插件市场（P6） |
| **Apache APISIX** | 路由创建拆成「匹配规则 → 插件链 → 上游」分步向导；插件选择用卡片+搜索 | 新建路由向导（P3）五步法 |
| **Higress 控制台** | 中文语境、域名→路由→服务来源的分层；AI/插件市场卡片化；监控内嵌 | 中文大白话文案 + 内嵌监控（P8） |
| **Nginx Proxy Manager** | 「完全不懂 Nginx 也能配」：域名+转发目标两个必填，其余全部可选折叠 | 「不懂概念也没关系」右侧栏（P3）+ 默认值先行 |
| **n8n / Node-RED**（流程编排参照） | 节点库拖拽 + 属性面板 + 连线即数据流；空画布给模板 | 流程编排画布（P4）布局语言 |
| **AWS API Gateway**（反例） | —— 资源树+方法表单极其晦涩，是「概念直译」的典型 | 作为反面教材，凡表单必配大白话与预览 |

调研来源：[Traefik Dashboard 文档](https://doc.traefik.io/traefik/reference/install-configuration/api-dashboard/) · [Kong Manager](https://developer.konghq.com/gateway/kong-manager/) · [APISIX 配置路由](https://apisix.apache.org/zh/docs/apisix/getting-started/configure-routes) · [APISIX Dashboard](https://apisix.apache.org/zh/docs/apisix/dashboard) · [Higress 控制台/观测](https://higress.ai/blog/higress-gvr7dx_awbbpb_hi9x7swfqgq1nqn2) · [Nginx Proxy Manager](https://github.com/NginxProxyManager/nginx-proxy-manager)

## 三、设计原则（v2 的四条铁律）

1. **先给地图，再给表单** —— 每个对象先看到它在流量链路里的位置（P1 拓扑 / P7 链路 / P4 画布），编辑只是地图上的一个点。
2. **一个请求的旅程可解释** —— 匹配 → 插件 → 转发 → 响应，每一跳有耗时、有理由（P9 调试台直接回答「为什么走了这条路由」）。
3. **大白话 + 实时预览** —— 向导每步右侧长出迷你拓扑和配置预览；术语首次出现都带一句人话解释（P3）。
4. **变更永远可预期、可回退** —— 保存是草稿，发布走「diff → 试运行 → 灰度 → 全量」（P10）；任何发布页都能一键回滚。

## 四、信息架构 v2

```
总览        拓扑总览（新，首页）
路由        路由列表（可视化改造）· 流程编排（画布升主入口）· 决策树视图（新）· 发布与版本（新）
插件        插件链编排（新）· 插件市场（升级）
可观测      监控大盘（增强）· 调试台（新）
系统        服务与上游 · 用户权限 · 系统设置
```

对比现状：路由/插件/用户 9 个重名分组 → 按任务域重组；画布、决策树、发布从「隐藏动作」升级为一级入口。

## 五、10 张原型清单（prototype-v2/）

| # | 文件 | 解决什么 |
|---|------|----------|
| 01 | `01-overview-topology.html` | 首页即流量地图：网关→分发→后置→上游全链拓扑 + 待处理 + 实时事件 |

## 六、实施路径（旧前端不删除）

**落地形态（推荐 B）：**

- 方案 A：独立新应用 `gateway4j-admin-ui-v2/`（端口 9303，同 API）。隔离最干净，但登录态/代理/构建全部要复制一份。
- **方案 B（推荐）：同仓并行子树** —— `src/views-v2/` + `src/layouts/LayoutV2.vue`，路由挂 `/v2/*`（旧路由原样保留在 `/`），顶栏加「新版体验」切换入口；按页面逐个搬迁，全部稳定后（单独一轮确认）再讨论是否删旧。构建、代理、登录、权限零新增基建。

**分期：**

| 期 | 内容 | 依赖 |
|----|------|------|
| P0 | 02 路由列表可视化改造 + 03 新建向导 + 10 发布与版本（后端已有 version/草稿语义） | 无新后端接口（列表页加命中量/链路摘要聚合接口，1 个） |
| P1 | 01 拓扑总览 + 05 决策树视图 + 07 路由详情 | 监控数据已有 Prometheus；决策树需要路由关系聚合接口（1 个） |
| P2 | 04 流程编排画布升级 + 06 插件链编排 + 09 调试台 | 调试台需要影子请求接口（1 个）；画布复用 Vue Flow |

## 七、验收标准

- 新用户不看文档能完成「建一条转发路由并发布」≤ 3 分钟（向导路径）。
- 任意一次线上问题，能在调试台回答「命中了哪条规则、哪个插件慢了」。
- 每次发布前能看到 diff 与影响面；灰度中可回滚。
- 旧页面行为零变化；权限模型沿用 `meta.permission`；Hallmark 各门槛（对比度/焦点环/折行/PRM）在新界面同样全过。
