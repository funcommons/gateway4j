# gateway4j 数据面验证报告（2026-10-28）

- 验证方式：黑盒 HTTP（Playwright request 上下文，无浏览器页面），spec 可重复执行
- spec / config：`gateway4j-admin-ui/e2e-gateway/data-plane.spec.ts`、`gateway4j-admin-ui/playwright.gateway.config.ts`
- 运行命令：`cd gateway4j-admin-ui && npx playwright test --config=playwright.gateway.config.ts --reporter=list`
- 最终结果：**5 个场景全部失败（5 failed）**，但所有失败收敛到同一个数据面结构性根因（见第 5 章）；每条失败都带完整黑盒证据
- 约束遵守：未重启/kill 9300（PID 21744，10-27 16:45 启动）、9301、9302 任何进程；未修改 src/**、gateway4j-engine/** 产品代码；测试产生的 gwtest_ 路由/插件已由 spec afterAll + DB 兜底清理（已核实库中 0 残留）

## 1. 结论摘要

1. **动态路由在 SCG 层注册时没有路径谓词（always-match）、也不过滤状态**。只要库里存在任意一条 BACKEND 路由，所有请求（无论路径是否匹配、路由是否 PUBLISHED）都会被转发到"排序恰好靠前"的那一条路由的 upstream。当前该 upstream 是历史回归残留路由指向的 `http://127.0.0.1:19000`（无服务时返回 500「系统繁忙」），**新建路由无论路径还是发布状态如何，永远分不到流量**。
2. **DISPATCH 分发路由与条件匹配完全没有接入数据面**：请求携带 x-ver=v1/v2 的分流断言实测全部命中同一个 upstream。
3. **插件链没有接入数据面**：ROUTE 级 Mock 插件（PRE、短路返回）绑定成功、ENABLED，但转发行为零变化。
4. **配置同步只有 30s DB 版本号轮询这一条通道**，无 WebSocket、无 Redis pub/sub；且因版本号按行自增，新路由"首次发布"（v1）不必然超过库中现存 max 版本，可能**永不触发 reload**（ADR-002 宣称已采纳的 WebSocket 推送在代码中不存在）。
5. 未匹配路径不返回 404：要么被转发到抢流路由的 upstream（200），要么随 upstream 连接失败变成 500「系统繁忙」。

## 4. 各场景验证方法

- **echo 后端**：spec 自带 `echo-server.cjs`（node http），beforeAll 拉起 3 个实例（19001/19002/19003），响应 `{echo:true, tag, path, method, header_x_echo, header_x_ver, body}`。**网关不改写路径**，因此场景归属只能靠 upstream 端口（tag）判定，而不能靠回显路径。
- **归因手段**：所有断言都要求响应体 `tag` 等于本场景 echo 的 tag，防止被抢流路由"恰好也返回 200"造成假通过。
- **配置生效等待**：每场景把路由 `config_version` 通过 publish/offline 循环推到「库内 max(routes∪plugins config_version)」之上（`publishAboveBaseline`），确保 30s 轮询必然触发 reload；随后 `expect.poll`（45s 上限、2s 间隔）轮询网关。测试 timeout 180s。
- **场景 2**：子路由 upstream 分别指向 19002/19003 两个不同 echo 实例，DISPATCH 父路由带两条 `HEADER x-ver EQ v1/v2` 条件（priority 1/2），按响应 tag 判定命中归属。
- **场景 3**：先轮询确认"下线前已生效"（前置），下线并把 version 推到新基线之上，再轮询确认"不再由本 echo 服务"。
- **场景 5**：`GET /v1/plugins` 记录 ENABLED 清单；创建 ROUTE 级 Mock 插件（可短路、外部可观察性最强）→ enable → 建路由时 `bindings` 绑定 → 发布 → 轮询。若 Mock 短路则断言通过；否则降级断言「绑定持久化 + 转发仍通」并在输出中说明。
- **清理**：每用例结束即 API 删除自己的路由（PUBLISHED 先下线）；afterAll 再做一次 DB 兜底清扫（gwtest_% 路由/条件/绑定/插件），并核实 0 残留。

## 5. 根因分析（源码 + 字节码 + 黑盒三重证据）

### 问题 1（P0）：动态路由注册无路径谓词、无状态过滤 —— 单路由抢流，新路由不可达

`gateway4j-engine/.../route/locator/DynamicRouteLocator.java`：

```java
return Flux.fromIterable(routes)
        .filter(route -> "BACKEND".equals(route.getRouteType()))   // 不过滤 status：DRAFT/OFFLINE 同样注册
        .filter(route -> route.getUpstreamUrl() != null)
        .map(route -> Route.async().id(...).uri(route.getUpstreamUrl())
                .predicate(exchange -> true)                        // 所有路由永远匹配
                .build());
```

- SCG `RoutePredicateHandlerMapping` 取**第一条**匹配路由 → 库里所有 BACKEND 路由都 always-match 时，flux 顺序（Caffeine `asMap()` 哈希序）决定唯一赢家，与请求路径无关。
- 运行中 jar 内同名字节码核实：`lambda$getRoutes$2` 返回常量 `iconst_1`（恒真谓词），与源码一致。
- 上游数据同样无状态过滤：`ServerAutoConfiguration.configService` 的 loader 为 `routeMapper.selectList(null)`（仅 @TableLogic 过滤 is_deleted）。
- 黑盒铁证（本次验证中多次复现）：网关对 `/totally/unrelated/xyz` 与对新建路由路径 `/e2e/gw/<run>/ping` 返回**完全相同**的 upstream 响应；在 19000 起一个监听后，所有请求（含未注册路径）都返回该监听的 `tag=winner19000`。
- **影响**：多租户/多路由场景下整个数据面等同于"所有流量进同一条路由"；404 兜底、路径匹配、发布状态全部失效。

### 问题 2（P0）：DISPATCH 分发决策未接线（死代码）

- `RouteDispatcher`/`RoutePathMatcher`/`RouteConditionMatcher`（HEADER/QUERY/BODY/GROOVY + 7 种操作符，实现本身完整）唯一的调用方是 `GatewayWebHandler`。
- `GatewayWebHandler` 只是 `EngineAutoConfiguration` 里的一个普通 @Bean，**从未被注册为 WebFlux 的主 handler**（bean 名非 `webHandler`，也没有 HttpHandler/WebHandlerConfigurer 定制），实际请求仍走 SCG 默认管线；且其 `onRouteResolved` 中"转发到后端"本身就是 placeholder 注释。
- 结果：管理面可创建 DISPATCH + 条件（创建/发布/画布接口全部成功），运行时零效果 —— 与场景 2 实测一致。

### 问题 3（P0）：插件链未接线

- 插件配置只进 `PluginConfigCache`；`GatewayWebHandler.setGlobalPrePlugins/setGlobalPostPlugins` **无任何调用方**；引擎也没有任何 SCG `GlobalFilter` 桥接。
- 黑盒：PRE 阶段、会短路返回的 Mock 插件绑定后转发行为零变化 → 所有 34 种内置插件在当前版本对流量均无效。
- **可观测性结论**：当前版本下，插件行为**全部无法黑盒断言**（绑定关系本身可通过管理面 API 断言，但那只是配置持久化，不是运行时行为）。

### 问题 4（P1）：新路由"发布"不保证触发配置同步

- `ConfigSyncService.checkVersion()`：仅当 `DB max(config_version) > localVersion` 才 reload；`config_version` 按**行**自增（publish +1、offline +1）。
- 新建路由首发布只到 v1；若库中已存在更高版本（本环境历史路由 v2），这次发布**永远不会**被轮询感知，直到该路由再经历 offline→publish（v3）或其他路由推高全局 max。真实用户会遭遇"发布了但网关不生效且无任何报错"。
- 本 spec 通过 `publishAboveBaseline`（publish/offline 循环推版本）绕开此坑，属于测试对缺陷的适配，不是产品正确行为的证明。

### 问题 5（P1）：404 兜底不可达

- 是问题 1 的直接推论：只要存在任一 BACKEND 路由，未匹配路径必然被转发（200）或随 upstream 失败变成 500（`{"code":10001,"message":"系统繁忙，请稍后重试"}`，网关异常处理器产出）。两种情况都不是规范意义上的网关 404。

### 问题 6（P2）：admin 无效 token 返回 500 而非 401；登录即踢旧 token

- 实测：同一账号再次登录后，旧 access_token 立即失效，且失效请求返回 `HTTP 500 {"code":10001,"message":"系统繁忙..."}`（毫秒级、无 DB/Redis 往返），而非 401。这会让"token 被踢"表现为服务端故障，干扰排障（本次验证过程中实际发生过一次误判）。
- 建议：token 校验失败应返回 401 + 明确错误码。

### 问题 7（P2）：ADR-002 与实现不符；gw_config_push_log 为空壳

- ADR-002 状态"已采纳"（WebSocket 推送 + 30s 兜底轮询），但代码中不存在任何 WebSocket 配置推送通道（gateway-boot 无 WS 客户端/监听器，无 Redis pub/sub）；`gw_config_push_log` 表 0 行，无读写方。文档应改为"规划中"或补齐实现。

## 6. ConfigSync 机制查证结论（任务要求项）

**结论：轮询之外没有任何即时通道。**

- 唯一同步路径：`ConfigPollingScheduler`（`@Scheduled(fixedDelay = ${gateway4j.config.poll-interval-ms:30000}, initialDelay = 30000)`）→ `ConfigSyncService.checkVersion()`（DB `max(gw_route.config_version, gw_plugin.config_version)` 对比本地版本）→ `ConfigService.loadAllConfig()`（全量重载路由/条件/插件 → `RouteDispatcher.updateRoutes` + 发布 SCG `RefreshRoutesEvent`）。
- 排除项（逐一核实过源码与字节码）：无 Redis pub/sub（`convertAndSend/MessageListener/ChannelTopic` 全库 0 命中）、无跨进程 WebSocket 推送（ADR-002 未落地）、admin 侧 `RouteService.publishEvent(ConfigChangeEvent)` 是 JVM 内 Spring 事件，不跨进程；`gw_config_push_log` 0 行、无读写代码。
- 实测收敛时间：路由版本推高后 ≤1 个轮询周期（≤30s）内网关生效（多个场景观测到 45s 轮询窗口内完成），与 30s 轮询机制吻合。

## 7. 插件链可观测性结论（任务要求项）

- 管理面 `GET /v1/plugins?status=ENABLED`：10 个全局内置插件 ENABLED（security、cache、cache-post、rate-limiter、sharing、sharing-post、logging、logging-post、tracing、tracing-post），另有 1 条历史 GROOVY 插件。
- 黑盒探针：Mock 插件（PRE、短路）是最强可观察插件；实测绑定后**无任何外部可见行为变化**。
- 结论：**当前版本所有插件行为均无法黑盒断言**（根因见问题 3：插件链不在请求路径上）；唯一可断言的是配置面持久化（绑定/启用接口返回）。场景 5 按任务约定降级为「绑定成功 + 转发仍通」，实测连"转发仍通"都因问题 1 不成立。

## 10. 修复建议优先级

1. **P0**：`DynamicRouteLocator` 为每条路由生成真实路径谓词（`Path=/x/**`），并只加载 `status=PUBLISHED` 的路由 —— 一处修复可同时恢复场景 1/2/3/4/5 的前提。
2. **P0**：把 `GatewayWebHandler`（或等效逻辑）真正接入请求管线（注册为 WebHandler 或实现为 SCG GlobalFilter），打通 RouteDispatcher 条件分发与插件链。
3. **P1**：配置同步版本语义改为全局版本（或发布时取 `max+1`），保证任何发布必然被轮询感知；ADR-002 的 WebSocket 推送要么实现要么改文档状态。
4. **P2**：admin token 失效返回 401；清理历史 e2e_* 残留路由（当前它们是抢流赢家并制造 500）。
