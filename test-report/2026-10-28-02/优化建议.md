## 1. 即时性：配置生效的最后一公里（P1，本轮最推荐）

### 1.1 落地 Redis pub/sub 推送，修订 ADR-002

**优先级 P1 · 工作量 S · 依赖：无（Redis 已在依赖里）**

**现状**：配置同步仅有 30s DB 轮询 + 内容指纹比对（C3 实现，可靠但慢）。数据面实测：路由发布后最长要等 30s 才生效；下线摘除同理。ADR-002 声称的 WebSocket 推送**至今未实现**——全库无 WebSocket/Redis pub/sub 代码，`gw_config_push_log` 表 0 行、0 读写方。

**大厂做法**：
- APISIX：配置存 etcd，Admin API 写入后**watch 事件毫秒级**推到数据面；
- Kong（DB 模式）：集群节点对 DB 做秒级轮询传播（gateway4j 现状≈此模式），Kong DB-less 则走声明式全量；
- Nacos：客户端**长轮询 29.5s 兜底 + UDP/gRPC 即时推送**，"兜底轮询 + 即时通道"双轨与本项目的现状+目标完全同构。

**建议**：admin 在路由/插件/全局插件写操作成功后向 Redis channel `gw:config:changed` publish；engine 订阅后触发 `loadAllConfig`（现有指纹比对复用为防抖与乱序保护）。落地细节：

1. 推送负载带 `{version, operator, source, changedType}`，作为 `gw_config_push_log` 的写入内容——这张表顺势成为**推送审计**（发布生效链路的追踪凭证，也回答"这次变更是谁推的"）；
2. engine 侧推送失败/订阅断连要打点（`gateway4j_config_push_failures_total`），推送通道挂了要能退化为 30s 轮询而不是静默滞后；
3. 推送成为主通道后，把轮询间隔从 30s 放宽到 60~120s 纯兜底，降低空转查询；
4. **文档同步**：ADR-002 状态从"已采纳"改为"部分实现（轮询）/ 本迭代补推送"，避免文档与代码继续背离——这是数据面验证报告明确点名的信任问题。

**验收**：发布路由后，用 `expect.poll` 断言数据面 <1s 生效（现有 `playwright.gateway.config.ts` 5 场景可直接改等待逻辑）。

### 1.2 发布流程的"生效确认"状态机

**优先级 P1 · 工作量 S · 依赖：1.1**

大厂控制台发布后给**确定性生效反馈**而不是"发布成功"就结束：阿里云 API 网关控制台发布 API 后列表状态会流转到"已发布（生效）"；Argo CD 的 Sync 状态机（Syncing → Healthy/Degraded）是同型范式。

**建议**：发布成功后前端轮询网关侧版本指纹（新端点 `GET /v1/monitor/config-version` 返回各 engine 实例已加载的指纹+时间），路由行内状态徽标流转「发布中 → 已生效 / 同步延迟」；超时（如 2×轮询周期）给黄色提示"网关同步延迟，点击查看引擎状态"。这同时兜住了 1.1 推送通道故障的可感知性。

## 2. 可观测：从"有页面"到"能定位问题"（P1）

### 2.1 插件执行可观测 + fail-open 语义分级

**优先级 P1 · 工作量 M（指标）/ S（fail-close 开关）· 依赖：无**

数据面 11 个插件已真实执行（fail-open），但**插件是否执行、耗时、是否被跳过对用户完全不可见**。`FailSafePluginChainRunner` 的 fail-open 是正确的兜底（broken 插件不能拖垮网关），但引出网关运维最危险的无声故障：**"你以为在生效的安全插件其实一直在抛异常被跳过"**。初稿已建议指标与告警，本增强版补三点：

1. **指标口径**：`gateway4j_plugin_execution_seconds{plugin, phase, result=ok|skipped|error}`（Counter + Timer 分开），错误率按 plugin 维度可查——这要求 runner 把 `log.warn` 处升级为同时打点（一行代码级改动）；
2. **fail-close 语义分级（新增）**：安全类插件（security/key-auth/jwt/sign/waf）应支持配置 `on_error: open|close`，默认 open 但允许关键路由声明 close——插件异常时返回 503 而不是放行。参照：Envoy 对关键过滤器默认 fail-closed；Kong 插件 PDK 允许插件声明自身失败语义。实现位置在 `FailSafePluginChainRunner` 加按插件的策略字段，S 级；
3. **管理面显式呈现**：内置插件卡片加"数据面已接线 / 未接线"徽标（数据源即 `PluginInstanceRegistry`，见 0.1-1，可做成 `GET /v1/plugins/runtime-status` 一个接口），路由详情的"插件绑定"Tab 对**绑定了无实例插件**的行给出警示条——用户当前完全无法从 UI 发现"绑定了个永远不运行的插件"。

### 2.2 路由级真实请求指标：先点亮，再接深

**优先级 P1 · 工作量 S（第一步）/ M（第二步）· 依赖：无**

修正后的根因见 0.1-2。分两步：

1. **第一步（S，快赢）**：把 `MetricsPlugin`（代码已存在于 `gateway4j-plugin-builtins/.../metrics/`）注册进 `ServerAutoConfiguration` 的实例清单并补一条集成测试——大盘的 QPS/错误率/延迟立即从"恒 0"变为真实值，监控三 Tab 从演示页变成可用页；
2. **第二步（M）**：指标持久化与多实例聚合。Micrometer 默认进 Prometheus 抓取路径后，admin 大盘改为读 Prometheus（或网关异步上报 Redis 累加）。注意当前 `MonitorController.routeMetrics` 把**同一个总量值平铺到每个时间点**（`data_points` 全等），第二步要一并修成真实时序，否则时间范围/粒度切换是假的。

这是"网关平台"与"网关 demo"的分水岭，且第一步成本被初稿高估了一个量级——建议提进 P1-a 快赢包。

### 2.3 变更记录、审计落库与并发保护

**优先级 P1（审计）/ P2（diff 回看）· 工作量 M · 依赖：无**

- **审计落库**：`InMemoryAuditSink` 重启即丢，framework4j-audit 的 Hash Chain 已具备只差 DB sink。落地后"变更记录"Tab 从"对象 updated_at 列表"升级为**操作流水**（谁/何时/对什么/做了什么/结果）；
- **配置 diff 回看**：变更记录每条可点开 before/after。快照机制（`gw_import_snapshot`）与画布 apply 的 dry-run diff（C5/C4 已实现）均可复用；
- **乐观锁（补回上轮遗漏项）**：`gw_route.config_version` 已存在但前端未用于并发控制。两人同时编辑同一路由，后保存者静默覆盖前者。建议 PATCH 请求带 `expected_version`，不匹配返回 10402「当前状态不允许该操作」，前端提示"已被他人修改，请刷新"。参照：Argo CD 对过期 resourceVersion 的同步冲突提示、Generic CMS 的编辑锁。上轮建议 4.7 提过，本轮初稿遗漏，此处补回。

## 4. 平台化能力缺口（新增章：初稿完全遗漏，本轮重点补深）

> 初稿的主题是"把现有功能打磨到位"，但对照大厂网关平台（Kong Konnect / 阿里云 API 网关 / MSE / Higress），有四项**结构性能力**完全缺失。它们不阻塞当前上线，但决定产品能否服务"多团队、多环境"的真实组织，且后两项依赖第一项，需要尽早规划而非事后加装。

### 4.1 多环境管理（dev / staging / prod 路由隔离）

**优先级 P1（规划）/ P2（首期实现）· 工作量 L · 依赖：无（是 4.3/4.4 的前置）**

**现状核实**：`gw_route` 表无环境维度（列清单：id/route_name/route_type/path/upstream_url/status/parent_route_id/sort_order/remark/config_version/tags），`tags` 是逗号分隔字符串（V1.3.1），可承载约定但**无结构化约束、无隔离、无按环境发布**——同名路由在 dev 和 prod 各配一份、prod 发布不受 dev 验证约束，当前完全做不到。

**方案分三步（每步独立可用）**：

1. **约定层（S）**：路由标签规范 `env=prod` / `env=dev`，列表筛选与批量操作按标签分区。零迁移成本，但无强制力，只适合过渡；
2. **维度层（M）**：`gw_route` 加 `environment` 列（默认 `default`），发布动作带目标环境，数据面按部署实例订阅各自环境——engine 实例用 `gateway4j.env` 配置声明自己服务哪个环境。这是阿里云 API 网关的模型：**同一份 API 定义，发布到 TEST / PRE / RELEASE 三个环境，各有独立状态与生效版本**；
3. **隔离层（L）**：环境间配置不可见或按角色可见（prod 只读 + 发布走 4.3 审批），配合 Kong Enterprise 的 **Workspace**（配置 + RBAC 双隔离）与 Nacos **命名空间**（namespace 级配置隔离 + 按 namespace 克隆）两个成熟参照。

**界面形态**（大厂通用）：顶栏全局环境切换器（与第 5 章的"环境标识徽标"合并设计）+ 路由列表环境列 + 发布对话框的目标环境选择。

### 4.2 OpenAPI / 文档集成

**优先级 P2 · 工作量 M（自文档）/ L（导入）· 依赖：无**

**现状核实**：全后端无 springdoc/swagger 依赖，无 OpenAPI artifact。三件事按序：

1. **admin 自身暴露 OpenAPI（M）**：引入 springdoc 生成 `/v3/api-docs`。现有 CI 契约护栏是自研脚本做 URL diff，OpenAPI artifact 可让护栏升级为**标准 schema diff**（breaking change 检测），也让前端可生成类型；
2. **路由 ↔ 上游 API 文档关联（M）**：路由详情页支持挂"文档链接 / OpenAPI 地址"，形成**API 目录**视图（按路由浏览所有上游服务的能力清单）。参照：阿里云 API 网关控制台的 API 列表即目录（每个 API 点开有请求/响应定义）；Kong Konnect 的 API Catalog 把网关对象与 spec 关联；
3. **从 OpenAPI 导入生成路由草稿（L）**：上传 spec → 按 paths 自动生成路由骨架（path/method/upstream 预填）进导入预检 diff 流程（复用 C5 的 Diff 表格）。参照：阿里云 API 网关"导入 API（基于 Swagger/OpenAPI）"是上线多年的成熟功能。这会把"新服务接入网关"从手工配置变成半自动，是对平台采用率影响最大的单项。

### 4.3 灰度发布工作流（发布审批 + 变更窗口）

**优先级 P2 · 工作量 L · 依赖：4.1（环境维度）、2.3（审计落库）**

**现状**：`publishRoute` 是一键操作——草稿即发布、发布即全网生效、无审批、无窗口、无发布后验证。个人项目够用，多团队组织里"谁在周五下午改了 prod 路由"是无解问题。

**建议（分两档）**：

- **轻量档（M）**：发布对话框强制填写**变更说明** + 显示 dry-run diff（复用画布 apply 的 diff 组件）+ 发布记录进审计流水。零新表，先满足"可追溯"；
- **流程档（L）**：发布单状态机 `草稿 → 待审批 → 排期中（变更窗口）→ 发布中 → 已生效/已回滚`。审批人按角色配置；变更窗口（如"仅工作日 14:00-17:00 可发布 prod"）在窗口外自动禁用发布按钮并给原因。发布后自动跑冒烟（复用数据面 spec 断言）失败即提示一键回滚（快照机制已有）。
- **参照**：Argo CD 的 **Sync Windows**（按时间窗允许/禁止同步，窗口外钉住）+ Sync 审批（人工确认才 apply）是开源界最完整的同型实现；GitHub PR 审批流是大家最熟悉的交互模板；阿里云内部变更平台的"变更单"是同构的企业实践（此处写通用范式，具体产品形态未公开细节，不编造）。

### 4.4 配置导入导出的环境间 diff

**优先级 P2 · 工作量 M · 依赖：4.1（至少到约定层）**

**现状**：导入预检 diff（C5 已做）比较的是"**导入包 vs 当前库**"；缺"**环境 A vs 环境 B**"——把 dev 验证过的配置搬到 prod 前，运维需要先看到两环境路由集的差异（新增/缺失/字段级不同）。

**建议**：导出包带环境指纹；导入导出页新增"环境对比"面板——选源环境 + 目标环境 → 逐条列出 `新增 / 缺失 / 变更（字段级 diff）/ 冲突`，勾选生成导入包进现有预检流程。参照：Nacos 控制台的**配置克隆（跨命名空间）+ 历史版本 diff 回滚**、Kong **decK** 的 `deck dump / deck diff`（声明式配置与在线状态对比是 decK 的核心交互）、Argo CD 的 App Diff 视图。全部复用现有 diff 组件，增量在数据源编排。

## 6. 国际化、主题与适配（新增章：初稿仅一句带过，本轮展开）

### 6.1 i18n 完整度收口

**优先级 P2 · 工作量 S · 依赖：无**

**现状核实**：双语词表与覆盖测试基建都在（`src/locales/zh-CN.ts` + `en-US.ts`，配套 `i18n-coverage.test.ts` / `en-US-quality.test.ts` / `locale-structure.test.ts` 四个护栏测试，这在同类项目里是少有的好底子），但**页面级遗漏仍然成片**。抽查证据——`Roles.vue` 中硬编码中文至少 15 处：'新建角色'、'备注'、'操作'、'编辑角色'、'保存成功'、'删除角色后不可恢复，确定删除？'、'请输入角色编码'、'全选'、'已选 x / y'、'暂无可分配权限'、'授权成功'等（script 与 template 两段都有）。

**建议**：
1. `eslint-plugin-vue-i18n` 的 `no-raw-text` 规则进 CI（template 层拦原生中文）；
2. `i18n-coverage.test.ts` 扩展一条：扫描全部 `.vue` template 与 ElMessage 调用里的 CJK 字符，白名单清零制；
3. 一并核对 Element Plus 组件内置文案的 locale 配置（el-table 空态/分页等默认英文或中文取决于是否定了 `ElConfigProvider locale`）。

### 6.2 暗色主题走查与双份截图基线

**优先级 P2 · 工作量 S–M · 依赖：无**

**现状核实**：SDK 的多主题能力**已经存在且超出初稿预期**——`styles/themes.scss` 定义了 `[data-theme="light"] / [data-theme="dark"] / [data-theme="orange-black"]` 三套项目级 token，`FcThemeSwitcher` 提供浅色/深色切换 + 8 个品牌 swatch（acme/apple/google/microsoft 等），`config/features.ts` 还有 darkMode 特性开关。能力在，缺的是**验证与兜住**：

1. 全页面暗色走查：Element Plus 组件（弹窗/表格/下拉）是否跟随 `[data-theme]` 变量、ECharts 图表配色是否跟随主题（图表硬编码浅色系是最常见的破绽）、`color-mix` 计算色在暗色下的对比度；
2. Playwright 截图基线做 **light/dark 双份**（第 7 章视觉回归的一部分），防止后续迭代只在浅色下自测；
3. 主题偏好随用户持久化（`gw_config` 已有存储，当前仅 localStorage，换设备即丢）。

参照：Element Plus 官方暗色模式（`html.dark` + CSS var 覆盖是标准做法，本项目 token 方案与其同构）；Grafana 的 light/dark 双主题仪表盘配色规范。

### 6.3 窄屏与移动端适配

**优先级 P2（1366 底线）/ P3（移动端）· 工作量 S / M · 依赖：无**

管理后台产品**桌面优先**是大厂共识，但两级底线要明确：

1. **1366×768 不横滚（S）**：主流办公本分辨率。低优列（描述/标签/更新时间）在 `≤1440px` 隐藏、操作列按 5.2 收纳，即可达成；
2. **移动端只读大盘（M，可选）**：不做移动端全功能（画布在触屏上无解，不必勉强），只做 `/dashboard` 的响应式只读视图——"值班时手机上看一眼网关状态"是运维真实场景。`FcSidebar` 已有 `useResponsive` 折叠能力可复用。

参照：阿里云/腾讯云控制台普遍声明桌面优先但在窄屏下做列降级；Grafana 移动端是典型"只读查看"定位。
